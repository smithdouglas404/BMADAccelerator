## Agent memory: Mem0 + Letta

Doug's rule, and the one future sessions keep forgetting. Read it before touching agents, memory or generated apps.

- **Letta** (self-hosted, open source, `letta` in `docker-compose.yml`) is the stateful agent runtime. A Letta agent has a persistent **persona** (who it is, its voice and role) and per-person **memory blocks** (the human it talks to) that it edits itself as it learns. That gives an agent a stable identity across weeks, not just recall.
- **Mem0** (self-hosted, open source, `mem0` in `docker-compose.yml`, OpenAI embeddings) is long-term **fact** memory: what was said, decided and learned, searchable later. Scoped per customer and per use case, so one product's agents never see another's.
- Never the cloud versions of either.
- **Every newly identified agent gets a Letta persona by default**, with Mem0 for its long-term facts. The "Stateful persona" setting starts **on**; it goes off only when a person explicitly says so (for example a simple background task agent they don't want to pay for). Socra proposes each agent with its persona written out.
- Both run inside the **shared agent service** (`agent-service/`), with Inngest AgentKit orchestrating: agents are registered as configuration (name, instructions, persona, tools, model, approval steps), not coded per app. Generated apps call the service; they hold no model keys. Approvals (Approve / Reject with a comment) and run history live in the service. The package exports each agent's configuration plus a self-host option.
- **Use the maximum features of Letta and Mem0, always (Doug, Nov 21).** Before designing or changing anything that touches agents or memory, read the CURRENT open-source, self-hosted Letta and Mem0 documentation and compare it with what the code calls; do not rely on memory of what they can do. Prefer a feature they already offer (archival memory the agent writes itself, shared blocks, sleep-time reflection, per-person blocks, conversations, hybrid search, history, expiry, custom extraction) over building our own. When a feature is not used, say why in the PR. Never use cloud-only features (Mem0 graph memory is platform-only). Open items are listed in the thread "Give every agent memory and a brain screen" (features table, Nov 21).
- **Every specialist has the same memory** (Doug, Nov 21): Socra, Validator, UX, Engineer, Business analyst, Solution architect and a general Domain expert are fixed roles; a field's expert ("Claims expert") gets its own Letta persona and Mem0 id (`domain-<field>`) the first time its field is named (`specialistRoleKey`, `domainRole` in `lettaCore.ts`; created lazily in `letta.ts`). Specialists' findings and settled areas are saved to their own memory; an approved decision runs `onGatePassed`. Every read and write is counted (`MemoryEvent`, `logMemoryEvent`) and Settings > Agent memory shows "Is it used?" (read, written, write-only) from those counts (`usageCore.ts`, tested in `tests/agentmemory.test.mjs`).
- **Letta and Mem0 features in use beyond persona and facts** (Doug, Nov 21): each role's own Letta archive (findings saved with `archiveWrite`, searched by meaning each turn and by `search_memory`, kept per customer by tag), one standalone Letta block per customer that holds that customer's decisions (`playbookAppend`/`playbookRead`, read each turn, never attached to the cross-customer roles), a `human` block per role (what it learns about each person, filled from gate messages), Letta's sleep-time reflection agent where the server accepts it (state shown on the memory page), Mem0 record history on the memory page, and Mem0 hybrid-search packages in `memory/mem0/Dockerfile`. Not used and why: Letta conversations (API not verified on the self-hosted 0.16.8), Mem0 custom extraction prompt (needs the full server config re-sent), Mem0 graph memory (platform-only), Letta channels (not needed). Each use is counted in `MemoryEvent`.
- The Studio's own agents (Socra and its specialists) also keep their working mind in Letta and their long-term memory in Mem0 (`src/lib/memory/`).
- **Settings > Agent memory** (Doug, Nov 21) shows every agent's Letta blocks and Mem0 facts exactly as stored, filtered by customer and use case, read-only. Its plain-language narrative is written by the document model (Haiku) only when a person presses Explain, from exactly those records; every sentence must cite a record or it is dropped, and the model, time and records read are kept (`MemoryNarrative`). Rules in `src/lib/memory/inspectCore.ts` (tested in `tests/memoryview.test.mjs`). Until sign-in is on, the page and every `/api/memory` route answer only on the Studio's own computer (localhost:3000), never through the Cloudflare tunnel (`isLocalRequest` in `src/lib/localOnly.ts`, Doug, Nov 21).

Checks before pushing: `npx tsc --noEmit`, `npm run lint`, `npm test`, `npm run build`.

## Test before you tell Doug to move anything

Doug, Nov 22: "Anytime you make a fix or a change, you test it before you actually tell me to move it forward. There should be no reason why you tell me to push, etc., and it hasn't gone through a test. I don't want to see any code come to me that hasn't actually had a green light."

This is a standing rule for every thread and every agent that works on the Studio:

1. **Green before the ask.** Before telling Doug to push, merge, install, update, press a button or paste a command (including the laptop's one-line update), the change must have passed all of these, run on the final commit:
   - `npx tsc --noEmit` (it compiles) and `npm run lint` (no errors);
   - `npm test` (every test passes; a new behaviour gets a test that fails without it);
   - `npm run build` when the change touches routes, the database schema, Docker or build scripts;
   - a check that the feature itself works on a running copy (start the app or its stand-in, use the feature, see the result), and for the laptop's Podman build, the commands run against that build's real files.
2. **A command is code.** A shell line, a migration or a script given to Doug is tested the same way before it is given; run it in the sandbox where it can run, and say where it could not.
3. **Say what was run.** Every report names the checks and their results ("tsc clean, 135 of 135 tests, build passed, feature used on a stand-in"). Never write "should work".
4. **Untested means unsent.** If something could not be tested (no Docker here, no real Letta, no Mac), the report says so plainly, names exactly what was not covered, and does not ask him to move it forward; either find another way to test it or ask the thread that can.
5. **A failure is reported, not hidden.** If a check fails, fix it and run again before telling him; if it cannot be fixed, say so and do not move the change forward.
6. **Never skip, quarantine or weaken a test to get green.**
